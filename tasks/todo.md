# v3.0.0 — план мажорного релізу

Мета: закрити всі відомі розриви (протокол MCP, покриття Jira API, надійність), прибрати
надлишковість логіки і не зламати жодної наявної поведінки.

Стан на старті: 54 інструменти, 34 промпти, один файл `src/index.ts` (~4700 рядків),
нуль автотестів у репозиторії.

### Розриви протоколу MCP

- `capabilities` містить лише `tools` і `prompts`
- нуль анотацій інструментів (`readOnlyHint` / `destructiveHint` / `idempotentHint`)
- нуль `outputSchema` / `structuredContent` — усе повертається як `JSON.stringify` у текстовому блоці
- промпти без аргументів: `ListPrompts` віддає лише `name` + `description`
- немає `completion/complete`
- немає ресурсів

### Розриви покриття Jira

Спринти (create/update/state), версії (create/update/release/delete), компоненти (CRUD),
`editmeta` як інструмент, масове редагування полів, віддалені лінки, видалення вкладення,
видалення лінка, `mypermissions`, статуси проєкту, список міток, ранжування, беклог,
`fields`/`expand` у пошукових інструментах, видимість коментарів (internal/JSM).

## Рішення, які треба ухвалити до старту

### D1. Розбивати `src/index.ts` на модулі?

`CLAUDE.md` фіксує однофайлову архітектуру як свідому ("simplifies build, no module
resolution surprises for npx, easier to audit"). Після цього релізу файл буде ~7000 рядків.

- **Рекомендація: розбити**, помірно — 10-12 файлів за доменом, без мікромодулів.
  `tsc` компілює в `dist/` зі звичайними відносними ESM-імпортами, для `npx` нічого не
  змінюється; аудит стає легшим, а не важчим, бо безпекові інваріанти збираються в один
  `validation.ts` замість розсіювання по 4700 рядках.
- Альтернатива: лишити один файл із секціями-регіонами. Тоді фази 1 і 4 роблять те саме,
  але навігація по файлу лишається важкою.
- **Це рішення ваше — воно переписує задокументовану конвенцію проєкту.**

### D2. Що робити з надлишковими інструментами?

`jira_list_epics`, `jira_get_user_issues`, `jira_search_by_filter`, `jira_get_board_epics`,
`jira_get_attachments` — це `jira_search_issues` / `jira_get_issue` з фіксованим JQL або
набором полів.

- **Рекомендація: залишити всі імена, але перевести на спільне ядро** (тонкі обгортки над
  одним пошуковим движком) і позначити в описі канонічний інструмент. Прибирає надлишковість
  *логіки*, не ламаючи жодного наявного сценарію і жодного промпта.
- Альтернатива: видалити 5 інструментів у мажорі. Чистіша поверхня, але ламає промпти
  користувачів і будь-яку їхню автоматизацію.

### D3. Примусова англійська від Jira

`Accept-Language: en-US` + `X-Force-Accept-Language: true` (перевірити на вашому інстансі
одним curl) змусили б Jira віддавати канонічні назви і зняли б проблему локалізації в корені.

- **Рекомендація:** env `JIRA_FORCE_ENGLISH` (типово `false`), бо вмикання змінює те, що
  користувач бачить у відповідях. Резолюція name->id лишається як була і працює незалежно.

### D4. Обсяг ламких змін

Мажор дозволяє ламати. Пропоную рівно три ламкі зміни, кожна — усунення несумісності:

1. `assignee` у всіх списках стає об'єктом `{accountId, displayName}` (B3)
2. Пагінація уніфікується: `{total, isLast, nextPageToken, startAt}`; поле `count` зникає (R6)
3. Форма елемента списку задач стає однаковою для всіх інструментів (R2)

Все інше — адитивне. Перейменувань інструментів немає, видалень немає.

## Фаза 2 — Надійність (закриває B4, B5)

## Фаза 4 — Протокол MCP

### 4.1 Анотації (дешево, ефект одразу)
- [ ] `readOnlyHint` на всіх `get_*` / `list_*` / `search_*`
- [ ] `destructiveHint` на `delete_*` і на `jira_update_sprint` зі станом `closed`

- [ ] `openWorldHint: true` (сервер ходить у зовнішню систему)
- [ ] Перевірити на реальному клієнті, що читання перестало питати підтвердження

### 4.2 Структурований вивід
- [ ] ~12 спільних схем (`Ack`, `Issue`, `IssueList`, `MetaFields`, `Transitions`, `UserList`, `Paged<T>`, ...) на всі інструменти — не 70 рукописних схем

- [ ] Тест: `structuredContent` валідується проти власного `outputSchema` для кожного інструмента
